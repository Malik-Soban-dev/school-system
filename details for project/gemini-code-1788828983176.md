This document maps out how the different platforms, services, and environments in the "School-System ERP" communicate with each other.

## 2. The Three-Tier Environment Map

To understand how the project works, it is divided into three distinct environments that must seamlessly connect:

### A. The Local Development Environment (The Builder)
* **OS / Server:** Windows 11 / Laragon
* **Runtime:** PHP 8.3.33 (Command Prompt / `cmd.exe`)
* **Role:** Where code is written, dependencies are downloaded (Composer), and version control (Git) is managed. 
* **Integration Quirk:** Because local PHP (8.3.33) is older than some production package requirements, we use `composer config platform.php 8.4.0` to trick Composer into downloading the correct production packages.

### B. The Hosting Environment (The Engine)
* **Platform:** Render
* **Runtime:** Custom Docker Container (PHP 8.3-fpm / Linux)
* **Role:** A stateless web server that runs the application 24/7. It listens for GitHub updates, rebuilds the Docker image, installs production dependencies, and serves the Laravel app.

### C. The Data Environment (The Brain)
* **Platform:** Turso
* **Database Type:** Serverless Edge libSQL (A distributed version of SQLite).
* **Role:** Stores all user, school, and academic data. It sits completely separate from the Render web server to ensure data is not lost when Render restarts or scales the Docker container.

---

## 3. How Everything Connects (The Pipeline)

Here is the exact step-by-step flow of how a line of code travels from your computer to the live server and interacts with the database.

### Step 1: Local to GitHub (Version Control Sync)
* **Mechanism:** Git CLI push.
* **Flow:** You write code in Laragon -> Run `git push origin main` -> The code is uploaded to the GitHub `school-system` repository.

### Step 2: GitHub to Render (Automated Deployment)
* **Mechanism:** GitHub Webhooks.
* **Flow:** Render is linked to your GitHub repo. The moment GitHub receives a new push to `main`, it pings Render. Render automatically pulls the fresh code and begins reading your `Dockerfile` to build a new Linux server environment.

### Step 3: Render Internal Build (The Docker Lifecycle)
* **Mechanism:** Render Build Engine + Dockerfile.
* **Flow:** Render installs `zip` and `unzip`, injects Composer, and runs `composer install`. Once built, Render triggers your boot script: `php artisan migrate --force && php artisan serve`.

### Step 4: Render to Turso (The Database Connection)
* **Mechanism:** HTTP/WebSockets via `turso/libsql-laravel` package.
* **Flow:** The Laravel app on Render needs data. It looks at its Environment Variables (see Section 4). Using the custom `libsql` driver in `config/database.php`, Laravel sends secure SQL queries over the internet directly to Turso's edge nodes and retrieves the data in milliseconds.

---

## 4. The "Glue": Crucial Environment Variables
For the Render to Turso integration to work, the following environment variables MUST be configured in the Render Dashboard:

* `DB_CONNECTION=libsql` (Tells Laravel to use the Turso package, not standard MySQL/SQLite)
* `DB_URL=libsql://[your-database-name].turso.io` (The exact endpoint of your Turso database)
* `DB_AUTH_TOKEN=[your-long-turso-jwt-token]` (The cryptographic key that proves Render is allowed to access Turso)
